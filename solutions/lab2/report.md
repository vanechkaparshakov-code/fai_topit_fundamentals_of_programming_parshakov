## Связи объектов после переназначения

**До переназначения `second`:**

```text
first ──────┐
            ▼
        ┌───────────┐
        │ [10, 20, 30] │
        └───────────┘
            ▲
second ─────┘
```

Имена `first` и `second` ссылаются на один объект списка. Поэтому изменение списка через одно имя отражается при обращении через другое.

**После переназначения `second = [10, 20, 30]`:**

```text
first ──────► ┌──────────┐
              │ [10, 20, 30] │
              └──────────┘

second ─────► ┌──────────┐
              │ [10, 20, 30] │
              └──────────┘
```

Теперь имена `first` и `second` ссылаются на разные объекты, хотя содержимое списков одинаковое. Поэтому `first == second` возвращает `True`, а `first is second` — `False`. Изменение списка `second` больше не влияет на список `first`.


При переназначении second на новый список с теми же элементами имя second привязывается к новому объекту, поэтому id first и second не совпадают (#1). При first == second результатом сравнения будет True, т.к. списки одинаковые, а при first is second – False, т.к. объекты разные (#2). При изменении списка second список first никак не меняется, т.к. это два разных объекта (#3).

При создании матрицы с помощью выражения wrong_matrix = [[0] * 3] * 3 внутренний список создаётся только один раз, а затем трижды повторяется ссылка на него. Поэтому все три вложенных списка привязаны к одному объекту (у них совпадают id, как видно в первой строке вывода). При изменении элемента одного списка, изменения отображаются сразу во всех. Во втором случае создания матрицы на каждой итерации цикла создается новый внутренний список, каждый из списков представляет собой отдельный объект в памяти (третья строка вывода). При изменении элемента одного списка остальные списки остаются неизменными, поскольку их объекты независимы друг от друга.


### Вопросы для анализа.

- Поверхностная копия создает новый объект только для внешней части объекта, при этом внутренние объекты остаются неизменным, в отличие от глубокой копии.
- Глубокое копирование не следует применять автоматически ко всем объектам, поскольку оно требует дополнительных ресурсов памяти и времени на создание копий вложенных объектов.
- Поверхностной копии достаточно, если объект не содержит вложенных изменяемых объектов или если не требуется изменять их независимо от оригинала. В таких случаях глубокое копирование не нужно и приводит к лишним затратам ресурсов.

## Задание 3. Подсчет ссылок и время жизни объекта

### Исследование изменения счетчика ссылок
```python
import sys

data = [1, 2, 3]
print("После создания:", sys.getrefcount(data))

alias = data
print("После создания alias:", sys.getrefcount(data))

container = [data]
print("После помещения в контейнер:", sys.getrefcount(data))

del alias
print("После del alias:", sys.getrefcount(data))

container.clear()
print("После очистки контейнера:", sys.getrefcount(data))
```

### Результат
```text
После создания: 2
После создания alias: 3
После помещения в контейнер: 4
После del alias: 3
После очистки контейнера: 2
```


Sys.getrefcount() показывает на одну временную ссылку больше, потому что создается дополнительная временная ссылка при передаче этого объекта в функцию;

Счетчик увеличивают инструкции alias = data, container = [data];

Счетчик уменьшают инструкции del alias, container.clear();

Del alias удаляет имя, а не командует напрямую удалить объект, потому что del удаляет из памяти ссылку на объект, то есть имя a. К этому объекту можно обратиться по другой ссылке (в данном случае data).

### Эксперимент со слабой ссылкой
```python
import weakref

class Record:
    pass

record = Record()
weak_record = weakref.ref(record)
print(weak_record())
del record
print(weak_record())
```

### Результат
```text
<__main__.Record object at 0x000002C9608A5550>
None
```

Слабая ссылка не продлевает время жизни объекта, поскольку не препятствует его уничтожению. Если на объект не остаётся сильных ссылок, он может быть удалён из памяти. Слабые ссылки могут быть полезны для временного доступа к промежуточным результатам вычислений без дополнительного удержания объектов в памяти. Если результат больше не используется и на него не осталось сильных ссылок, объект может быть освобождён автоматически. Ниже представлен пример такой ситуации.

### Пример работы со слабыми ссылками
```python
class Result:
    def __init__(self, value):
        self.value = value

def calculate(n):
    return Result(n ** 2)

result = calculate(5)
cache = weakref.ref(result)
print(cache().value)
del result
print(cache())
```

### Результат
```text
25
None
```


### Практическая задача 2.

Сначала создается класс Record(), далее сохраняются сильные ссылки record_1 и record_2 на два объекта Record. С помощью weakref.WeakValueDictionary() создается словарь, в него добавляются слабые ссылки на все три созданных объекта Record. Третий объект удаляется сразу, потому что на него нет созданных сильных ссылок, остальные объекты удаляются после использования del ‘ссылка на объект’. Таким образом, слабый реестр не управляет временем жизни объектов. Ниже представлен код и результат работы программы.

```python
import weakref

class Record:
    pass

record_1 = Record()
record_2 = Record()

weak_record = weakref.WeakValueDictionary()
weak_record['1'] = record_1
weak_record['2'] = record_2
weak_record['3'] = Record()

print(list(weak_record.keys()))

del record_1
print(list(weak_record.keys()))

del record_2
print(list(weak_record.keys()))
```

### Результат
```text
['1', '2']
['2']
[]
```


### Вопросы для анализа.

Объект может быть освобождён, когда количество сильных ссылок на него становится равным нулю. Слабые ссылки не препятствуют его уничтожению.

Освобождение Python-объекта не всегда означает немедленный возврат памяти операционной системе. Освобождённая память может оставаться в распоряжении Python для повторного использования при создании новых объектов. Возврат памяти операционной системе не обязательно происходит сразу.

Сильная ссылка удерживает объект от уничтожения, пока существует. Слабая ссылка позволяет обращаться к объекту, но не препятствует его уничтожению, если на него больше не осталось сильных ссылок.


Функция gc.collect() запускает сборщик мусора вручную и возвращает количество объектов, найденных и освобождённых при сборке. Функция gc.get_threshold() показывает пороговые значения автоматического сборщика мусора, а gc.get_count() - текущие счётчики, связанные с его работой. После удаления переменных first и second циклические ссылки между двумя списками сохраняются. Поэтому обычного подсчёта ссылок недостаточно для их освобождения. При повторном вызове gc.collect() сборщик обнаруживает и освобождает два объекта, образовавших цикл. В классической модели CPython существует три поколения объектов: нулевое — для новых объектов, первое -для объектов, переживших проверки младшего поколения, и второе - для долгоживущих объектов. Новые объекты проверяются чаще, а старшие поколения — реже, что позволяет оптимизировать работу сборщика мусора.

### Вопросы для анализа.

- Циклическая ссылка возникает, когда объекты образуют замкнутый круг ссылок, т.е., например, первый объект ссылается на второй, а второй объект на первый.

В этом случае обычный подсчёт ссылок не позволяет определить, что объекты больше не используются, поэтому для их обнаружения и освобождения необходим циклический сборщик мусора.
- Сборщик мусора разделяет отслеживаемые объекты по поколениям для оптимизации своей работы. Новые объекты проверяются чаще, чем старые, потому что выше вероятность, что среди них есть ненужные объекты.

Размер списка не увеличивается после каждого append, потому что новая память выделяется только после того, как закончится зарезервированная.

Список резервирует место с запасом, чтобы при добавлении каждого нового элемента не приходить выделять дополнительную память. Это оптимизирует процесс добавления элементов.

Длина списка — это количество элементов в нём. Объём памяти, показываемый sys.getsizeof(), характеризует размер самого списка в байтах, включая память под ссылки на элементы и зарезервированную ёмкость.

## Итоговый анализ.

Существует несколько способов уменьшить избыточное потребление памяти в программах, работающих с большими объёмами данных.

Удалять ненужные ссылки на объекты. После завершения работы с данными следует удалять ссылки, которые больше не используются, чтобы объекты могли быть освобождены сборщиком мусора. Это рассматривалось в задании 3.

Использовать последовательности, которые генерируют значения по запросу. Например, range() хранит параметры диапазона, а не все числа сразу, в отличие от list(range(...)). Это позволяет значительно экономить память при работе с большими последовательностями. Этот способ рассматривался в задании 5.

Выбирать подходящие структуры данных и учитывать их особенности. Например, списки резервируют дополнительную память для ускорения добавления элементов.  ### Вывод об опасных ошибках при работе с изменяемыми объектами


1. **Случайное создание общей ссылки.** При присваивании `b = a` новый объект не создаётся. Изменения объекта через `b` также видны через `a`.

   ```python
   a = [1, 2]
   b = a
   b.append(3)

   print(a)  # [1, 2, 3]
   ```

2. **Поверхностное копирование вложенных объектов.** При поверхностном копировании создаётся новый внешний объект, но вложенные изменяемые объекты остаются общими. Их изменение может повлиять на оригинал.


3. **Создание матрицы умножением списка.** Выражение `matrix = [[0] * 3] * 3` создаёт несколько ссылок на один вложенный список. Изменение одного элемента может изменить соответствующий элемент во всех строках.
